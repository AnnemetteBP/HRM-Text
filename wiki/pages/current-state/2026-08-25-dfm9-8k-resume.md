# DFM9 8K Resume From Step 2137000

The existing scheduler plan `logs/scheduler/dfm8_L_campaign_epoch2_20260803`
was repaired and resumed. Training row `dfm9-8k-train-2150000` now resumes
from the complete checkpoint
`/work/dfm/HRM-Text-long-context/checkpoints/long-context/8k-from-4k-epoch8/ephemeral_step_2137000`
and stops at step `2,150,000`.

The run is `dfm9-xl-8k` in W&B project `DFM5`. It uses the 8K config, YaRN
factor 2.0, global/global attention, FSDP FP32 parameters, BF16 compute,
global batch 262144, gradient accumulation 2, and epoch 9 continuation.

At startup all eight ranks loaded the checkpoint and reported
`step=2137000`, `start_epoch=9`, and `skip_batches=19022`. The initial low GPU
utilization is therefore the expected resume batch-skip phase. The scheduler
is in tmux window `hrm-1:8:scheduler-8k`; the separate Rich monitor is in
`hrm-1:9:eval-monitor` with a 30-second refresh interval.

## Evaluation RoPE Configuration

The dedicated epoch-8 long-context baseline used the HF export
`exports/dfm9_XL_step_2127489_ema_hf_yarn2_8k`. Its `config.json` specifies
8,192 positions and YaRN factor 2.0 with an original context of 4,096. The
epoch-8 standard and DFM metrics cloned into the 8K W&B run are different:
they were inherited from the original 4K evaluation campaign and therefore
did not use the new 8K/YaRN serving path.

An audit on 2026-08-26 found that
`exports/dfm9_8k_step_2150000_ema_hf/config.json` specifies default RoPE,
despite the 2.15M checkpoint having been trained with YaRN factor 2.0. Until
that checkpoint is re-exported with the correct RoPE metadata and evaluated
again, comparisons involving its current evaluation results are confounded
and must not be interpreted as clean evidence about the effect of 8K
continued training.

### Corrective campaign

The exporter was corrected on 2026-08-26 to derive Transformers-compatible
YaRN metadata from the checkpoint configuration. Export jobs now validate the
RoPE type, factor, and optional expected context limit before accepting either
a new or an existing export. Pending exports from step 2.20M onward explicitly
expect YaRN factor 2.0 and 8,192 positions.

Step 2.15M was re-exported as
`exports/dfm9_8k_step_2150000_ema_hf_yarn2_corrected`; its verified config is
YaRN factor 2.0 with `original_max_position_embeddings: 4096`. A fresh full
standard, DFM, EuroEval, RULER-8K, and long-context campaign is queued in the
existing scheduler plan with fresh `step_2150000_corrected_yarn2` log roots.
The 2.20M training row is blocked on the corrected evaluation terminal barrier
and will resume from the complete `ephemeral_step_2152500` checkpoint.

Both training and the scheduler were deliberately stopped after this plan
repair. **Superseded 2026-08-26:** the stop request was subsequently cleared
and the scheduler resumed. It validated the corrected YaRN export and started
the fresh step-2.15M evaluation campaign on all eight GPUs. Training remains
blocked on the corrected evaluation terminal barrier and will then resume from
`ephemeral_step_2152500`.

The first corrected-evaluation launch produced 32 failed DFM IFEval-DA rows.
All failed before inference because `dfm-evals/.venv` lacked the declared
`ifeval` optional dependency `instruction_following_eval`; the scheduler's six
attempts per row could not repair this deterministic environment error. The
working recovery was:

```bash
uv pip install \
  --python /work/dfm/HRM-Text/dfm-evals/.venv/bin/python \
```

This installed commit `0c495b2f95155e8b10acb919ae283bfb4d5be6e2` plus

The corrected nine-task `long_context_headline_v3/overall` is `0.43098`,

the main driver (`0.57548 -> 0.76374`); excluding RULER, the other eight-task

## Expected Adaptation Budget

Published context-extension budgets span two distinct regimes. The YaRN paper
shows positional/perplexity adaptation in roughly 400 updates and reports that
YaRN needs 2.5 times fewer updates than positional interpolation. Code Llama's
broader 4K-to-16K long-context stage used 3,000--11,000 updates at 1--2M tokens
per update, while later work on robust downstream long-context capability uses
tens of billions of tokens. At this run's 262,144-token global batch, step
2,150,000 is 22,511 continuation updates and about 5.90B tokens after the 4K
epoch-8 boundary. Positional adaptation should therefore already have occurred;
robust task-level use can still improve through the remainder of the roughly
53.1B-token 8K epoch. Comparisons are not exact because YaRN and Code Llama use
much lower continuation learning rates (about `2e-5`) than this run's flat
`3e-4`, and modern studies emphasize retaining high-quality short-context data.

### Actual epoch-8 length distribution

A bounded scan of the installed `data/sampled_dfm9_8k/epoch_8` indices found
54,682,174 examples and 53.04B effective input tokens. Examples longer than
4,096 tokens account for 5,877,680 rows (10.75%) and 33.54B tokens (63.24%).
Prompts alone longer than 4,096 account for 4,581,931 rows (8.38%) and their
complete examples contain 27.22B tokens (51.31%). Because training is
target-only, a stricter supervision view is more informative: 4.39B of 11.61B
response tokens (37.80%) belong to examples longer than 4K, 1.24B response
tokens (10.64%) follow prompts already longer than 4K, and 2.26B response
targets (19.43%) occur physically beyond position 4,096. Multipacking does not
create cross-example long-context supervision because position IDs reset and
the variable-length attention boundaries isolate each example.

The principal chat sources are mostly short and therefore do not materially
change that conclusion. In the tokenized DFM9 8K source tree, English and
Danish repaired OpenHermes average 363 and 473 tokens respectively and have
effectively no rows above 4K; the synthetic Danish/English multiturn chat set
averages 380 tokens and has no rows above 4K. WildChat averages 1,572 tokens,
with 5.01% of rows above 4K but only 0.64% having prompts above 4K. The small
AI Arena Danish extract averages 1,393 tokens, with 8.65% of rows and 6.87% of
prompts above 4K, but contains only 4,569 source rows. The two WildChat task
aliases (`dfm_dyna_instruct/.../wildchat-qwen` and
`synquid_wildchat_100k_qwen_messages`) have byte-identical token and length
arrays, so they duplicate weighting rather than add breadth. These chat sets
remain useful for short multi-turn behavior and template following, but only a
small tail directly trains 4K-to-8K conversational dependency.

Source/converter audit, 2026-08-26. Confidence: high from the exported JSONL,
the OpenHermes repair code, and `scripts/tokenize_chat_template.py`. These chat
lengths are not caused by the DFM9 8K sampler or tokenizer truncation. The
tokenizer has no context-length limit, preserves the complete preceding
message history, and emits one example for every assistant turn. The final
repaired OpenHermes exports average 1,446 English and 1,504 Danish source
characters per conversation; the synthetic multiturn export averages 1,763.
Most are therefore intrinsically short. The OpenHermes teacher pipeline did
use an 8,192-token request budget and could reject exceptionally long requests
that did not fit, rather than clipping accepted rows; this affects only the
extreme tail and does not explain the overall short distribution. The
synthetic multiturn specification explicitly requested compact 2--6-turn
chats and imposed no post-generation truncation.

## Candidate Dedicated Long-Context Post-Training Data

Candidate review, 2026-08-26. Confidence: medium-to-high from the official
dataset cards and project repositories. Dedicated public long-context
post-training data does exist, but an exact 8,192-token training limit changes
the useful ordering:

- `zai-org/LongReward-10k` provides a 10K-row long-context QA SFT split plus
  two long-context DPO splits. Its English SFT rows are the strongest direct
  candidate after filtering rendered examples to fit 8K; reserve the DPO
  splits for an actual preference-training stage.
- `nvidia/ChatQA2-Long-SFT-data` provides roughly 195K English long-context
  RAG/conversational-QA rows. It is a useful high-volume candidate for the
  academic run, but needs exact tokenizer-based 8K filtering/windowing and is
  CC-BY-NC-2.0 with additional OpenAI-generated-data terms.
- `zai-org/LongAlign-10k` contains about 10K examples of 8K--64K tokens. Most
  examples cannot fit an exact 8K sequence once response and template tokens
  are included; use only a verified fitting edge subset now, or defer it to a
  16K/32K stage.
- `Yukang/LongAlpaca-12k` offers older long-document QA data and a balancing
  short subset. It is a secondary candidate behind LongReward/ChatQA2.
- `zai-org/LongCite-45k` contains long-document QA with sentence-level
  citations. It can teach grounded retrieval, but requires evidence-preserving
  window construction at 8K and should be capped so its special citation
  syntax does not dominate general answer style.
- `zai-org/LongWriter-6k` is primarily long-*output* SFT (2K--32K words), so
  much of it is incompatible with an 8K total sequence and does not directly
  solve long-input understanding.

For Danish and for precise control at 8K, project-specific context synthesis
from DynaWord, Folketing, GovReport-like, and other document sources remains
important. The NJUNLP context-synthesis recipe is particularly relevant: it
preserves high-quality instruction/answer pairs while generating supporting
and distracting background context, rather than replacing the target answer
with unconstrained synthetic output.

### Retained 8K post-training plan

This is a future data-preparation plan, not a claim that these sources are
already in the active epoch. Build a dedicated Gemma4-native 8K post-training
mixture with these gates:

1. Render with the installed tokenizer and Gemma4 template before deciding
   whether a row fits. Require `prompt + target <= 8192`; never clip a target.
2. Prioritize rows whose prompt crosses 4,096 tokens and preserve complete
   evidence needed by the target. Record both total length and the number of
   supervised target tokens physically beyond position 4,096.
3. Use the English SFT split of `zai-org/LongReward-10k` as the first public
   long-QA source. Keep its DPO splits out of ordinary SFT.
4. Add a tokenizer-filtered/windowed subset of
   `nvidia/ChatQA2-Long-SFT-data`, retaining answer-supporting passages and
   conversational history rather than taking blind leading-token crops.
5. Add a capped `zai-org/LongCite-45k` subset only after constructing windows
   that retain cited evidence. Keep its citation-formatted targets a minority.
6. Consider `Yukang/LongAlpaca-12k` only after quality and duplication review;
   it is a secondary source rather than a core source.
7. Generate matched Danish and English document QA, retrieval, multi-hop,
   summarization, instruction-following, and distractor-resistant examples
   from project document sources using the NJUNLP context-synthesis principle.
8. Keep high-quality short-context anchors in the post-training mixture to
   protect ordinary instruction following. Keep LongBench, RULER, Marathon,
   and all project long-context evaluation splits strictly evaluation-only.

Before sampling, report rows and rendered tokens by source and length bin,
prompt-only lengths, target lengths, and target tokens beyond position 4,096.
Run the existing short and long evaluation suites before and after this stage.

### Sources reserved for a 16K stage

At 16K, rebuild from source and re-render rather than reusing 8K-windowed
artifacts. Candidate sources are:

- the 8K--16K fitting portion of `zai-org/LongAlign-10k`;
- less aggressively windowed `zai-org/LongReward-10k` SFT;
- `nvidia/ChatQA2-Long-SFT-data`, including longer RAG and NarrativeQA rows;
- wider evidence-preserving windows from `zai-org/LongCite-45k`;
- the reviewed long portion of `Yukang/LongAlpaca-12k`;
- only the `zai-org/LongWriter-6k` examples whose complete prompt and target
  fit 16K, as a separately capped long-output capability slice;
- complete long conversations from `allenai/tulu-v2-sft-long-mixture`, after
  overlap and quality review; and
- newly synthesized 12K--16K Danish/English document tasks from DynaWord,
  Folketing, GovReport-like, and other approved document sources.

Do not promote examples into the 16K stage merely because they are long. Each
source must provide a target that actually depends on information distributed
through the extended context, or explicitly train controlled long output.
